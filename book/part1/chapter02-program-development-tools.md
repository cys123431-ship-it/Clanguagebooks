# Chapter 2. 프로그램 작성 과정과 개발 도구

## 이 장에서 배우는 것

- 소스 파일이 전처리·컴파일·어셈블·링크를 거쳐 실행 파일이 되는 과정을 순서대로 설명한다.
- 편집기, 통합 개발 환경, 컴파일러, 링커, 디버거가 각각 맡는 일을 구별한다.
- Visual Studio 2022에서 C 프로젝트를 만들고 `.c` 소스 파일을 추가하여 빌드하고 실행한다.
- `/std:c17`, `/W4`, `-std=c17`, `-Wall`, `-Wextra` 같은 옵션이 무엇을 정하는지 설명한다.
- 오류와 경고를 구별하고, 문제를 컴파일·링크·실행 중·논리 문제로 나누어 대처한다.

Chapter 1에서는 소스 코드가 그대로 실행되지 않고 번역·빌드 과정을 거친다는 점을 보았다. 이 장에서는 그 과정을 한 단계씩 나누어 살펴보고, 실제 개발 도구에서 그 과정이 어떻게 나타나는지 확인한다. 마지막에는 아주 짧은 C 프로그램을 직접 빌드하고 실행해 본다.

### 작성하고, 만들고, 실행하고, 확인한다

소프트웨어 개발은 흔히 요구 사항 분석, 설계, 구현, 테스트, 유지 보수의 단계로 설명한다. 무엇을 만들지 정하고, 해결 절차를 설계하고, 코드로 구현한 뒤, 여러 경우로 시험하고, 사용 중에 드러난 문제나 새 요구를 반영하는 흐름이다. 이 장에서 다루는 부분은 그중 **구현과 확인**이다.

구현 단계에서는 다음 순환이 반복된다.

```text
소스 코드 작성
      ↓
빌드 (실행 가능한 결과물 만들기)
      ↓
실행
      ↓
결과 확인 ──→ 기대와 다르면 소스 코드 수정으로 돌아간다
```

처음 만든 프로그램이 한 번에 완벽하게 동작하는 경우는 드물다. 빌드 단계에서 규칙 위반이 발견되기도 하고, 실행한 결과가 예상과 다르기도 하다. 따라서 이 순환을 빠르고 정확하게 반복하는 방법을 익히는 것이 이 장의 목표다.

### 소스 코드와 소스 파일

**소스 코드(source code)**는 프로그래밍 언어로 작성한 프로그램의 원문이고, 소스 코드를 저장한 파일을 **소스 파일(source file)**이라고 한다. C 소스 파일은 서식 정보가 없는 순수한 텍스트 파일이다. 글꼴이나 문단 모양을 함께 저장하는 문서 편집기 파일은 소스 파일로 쓸 수 없다.

C 소스 파일은 보통 `.c` 확장자를 붙인다. 이 확장자는 뒤에서 보겠지만 개발 도구가 파일을 어떤 언어로 처리할지 판단하는 기준이 되므로 단순한 이름 이상의 의미가 있다.

소스 코드는 사람이 작성하고 수정하는 프로그램의 원본이고, 뒤에서 설명할 목적 파일과 실행 파일은 그로부터 만들어지는 **빌드 결과물**이다. 소스 코드와 필요한 헤더·라이브러리 등의 의존 파일, 컴파일러·설정 등의 빌드 환경이 남아 있으면 목적 파일과 실행 파일은 다시 만들 수 있다. 사용자에게 배포할 때는 실행 파일과 함께 실행에 필요한 라이브러리나 데이터 파일 등을 전달하기도 한다.

### 소스 파일에서 실행까지

소스 파일이 실행되기까지의 큰 흐름은 다음과 같다.

```text
편집기 / 통합 개발 환경
        ↓  작성하고 저장한다
소스 파일 (예: hello.c)
        ↓  빌드한다 (컴파일러 도구 모음)
실행 파일
        ↓  실행한다 (운영체제가 적재하고 시작)
프로그램의 동작과 결과
```

**빌드(build)**는 소스 파일로부터 실행 파일 같은 최종 결과물을 만드는 전체 과정이다. 빌드 안에는 다음 절에서 볼 전처리, 컴파일, 어셈블, 링크가 들어 있다. 흔히 “컴파일한다”라고 말하지만, 엄밀히 말하면 **컴파일은 빌드의 한 단계**다. 빌드가 성공해야 실행할 수 있는 결과물이 생긴다.

**실행(execution)**은 운영체제가 실행 파일을 메모리에 불러와 프로그램을 시작하는 것이다. 실행 중에 프로그램은 화면에 결과를 표시하거나 입력을 받는다.

이 흐름의 각 단계를 실제로 어떻게 수행하는지는 사용하는 시스템에 따라 다르다. 명령어 한 줄로 빌드하는 환경도 있고, 메뉴에서 빌드를 고르는 환경도 있다. 처음 C를 배울 때 가장 큰 고비는 바로 이 기계적인 절차, 즉 소스를 작성하고, 빌드에 성공하고, 실행하고, 결과가 어디에 나타나는지 확인하는 일이다. 이 절차에 익숙해지면 이후의 학습은 언어 자체에 집중할 수 있다.

### 도구 모음이 나누어 맡는 일

빌드를 수행하는 도구들을 묶어 **도구 모음(toolchain)**이라고 부른다. C의 빌드 과정은 개념적으로 다음 순서로 나눌 수 있다.

```text
hello.c                    소스 파일
   ↓  전처리기(preprocessor)
전처리된 소스               #include, #define 같은 지시문을 처리한 결과
   ↓  컴파일러(compiler)
어셈블리 수준의 코드         언어 규칙을 검사하고 더 낮은 수준으로 번역한 결과
   ↓  어셈블러(assembler)
목적 파일(object file)      기계어 코드. 아직 완성된 프로그램은 아니다
   ↓  링커(linker)
실행 파일(executable file)  라이브러리 코드 등과 연결한 완성된 프로그램
   ↓  운영체제
실행
```

이것은 **개념적인 모델**이다. 실제 도구 모음은 몇 단계를 한 프로그램 안에서 처리하기도 하고, 중간 결과를 파일로 남기지 않기도 한다. 예를 들어 Visual Studio에서 쓰는 MSVC 컴파일러는 기본적으로 어셈블리 코드 파일을 따로 만들지 않고 목적 파일을 바로 만든다. 그래도 “지시문 처리 → 규칙 검사와 번역 → 기계어 코드 생성 → 연결”이라는 순서는 공통으로 적용된다.

### 전처리: 컴파일 전에 지시문을 처리한다

**전처리기(preprocessor)**는 본격적인 컴파일에 앞서 소스 파일에 적힌 **전처리 지시문**을 처리한다. 전처리 지시문은 `#` 기호로 시작하는 줄이다.

- `#include`는 다른 파일의 내용을 그 자리에 가져오도록 지시한다.
- `#define`은 어떤 이름을 정해 두고, 소스에서 그 이름을 정한 내용으로 바꾸도록 지시한다.

전처리 지시문은 값을 계산하거나 화면에 출력하는 C의 문장이 아니다. 컴파일러가 소스를 번역하기 전에 소스 자체를 준비하는 명령이다. 지시문의 자세한 문법과 사용법은 Chapter 20에서 다룬다.

### 컴파일: 규칙을 검사하고 번역한다

**컴파일러(compiler)**는 전처리된 소스가 C 언어의 규칙에 맞는지 검사하고, 맞으면 더 낮은 수준의 코드로 번역한다. 세미콜론이 빠졌거나 괄호의 짝이 맞지 않는 것처럼 규칙에 어긋난 부분은 이 단계에서 발견된다.

컴파일러가 검사하는 것은 **언어의 규칙**이다. 프로그램이 해결하려는 문제를 올바르게 푸는지는 컴파일러가 판단하지 못한다. Chapter 1에서 본 것처럼 배송비를 더해야 하는데 빼도록 작성한 코드도 규칙에는 맞을 수 있다.

### 어셈블: 기계어 코드를 만든다

**어셈블러(assembler)**는 어셈블리 수준의 코드를 프로세서가 실행할 수 있는 기계어 코드로 바꾸어 **목적 파일(object file)**을 만든다. 앞에서 말했듯이 이 단계가 컴파일 단계와 합쳐져 사용자에게 따로 보이지 않는 도구 모음도 많다.

목적 파일에는 소스 파일 하나를 번역한 기계어 코드가 들어 있다. 그러나 아직 완성된 프로그램은 아니다. 소스에서 사용했지만 그 파일 안에 정의가 없는 것, 예를 들어 화면 출력처럼 라이브러리가 제공하는 기능은 “다른 곳에서 찾아야 할 이름”으로 남아 있다.

### 링크: 필요한 조각을 연결한다

**링커(linker)**는 하나 이상의 목적 파일과, 프로그램이 사용하는 **라이브러리(library)** 코드를 연결하여 **실행 파일(executable file)**을 만든다. 라이브러리는 자주 쓰는 기능을 미리 만들어 컴파일해 둔 코드 모음이다. C 표준 라이브러리는 컴파일러 도구 모음이나 운영체제와 함께 제공된다.

링커의 핵심 역할은 **이름과 정의를 연결하는 것**이다. 목적 파일에 “다른 곳에서 찾아야 할 이름”이 남아 있으면 링커는 다른 목적 파일과 라이브러리에서 그 정의를 찾아 연결한다. 끝내 찾지 못하면 링크 오류를 보고하고 이번 빌드의 실행 파일을 완성하지 못한다. 링커는 C 문법을 검사하는 도구가 아니다.

프로그램이 여러 소스 파일로 나뉘어 있으면, 각 파일을 따로 컴파일한 뒤 링커가 목적 파일들을 하나로 묶는다. 그러면 한 파일만 고쳤을 때 그 파일만 다시 컴파일하고 링크하면 된다. 여러 소스 파일로 프로그램을 구성하는 방법은 Chapter 21에서 자세히 다룬다.

### 실행 파일과 파일 확장자

**실행 파일**은 링크가 끝나 운영체제가 적재하고 시작할 수 있는 형태의 프로그램이다. 실행 파일은 특정 운영체제와 프로세서 환경에 맞게 만들어진다. Chapter 1에서 본 것처럼 다른 환경에서 쓰려면 보통 그 환경에 맞게 다시 빌드해야 한다.

각 파일의 확장자는 **환경의 관례**이며, C 언어가 정한 규칙은 아니다.

| 파일 | Windows에서 흔한 형태 | Unix 계열에서 흔한 형태 |
|---|---|---|
| 소스 파일 | `hello.c` | `hello.c` |
| 목적 파일 | `hello.obj` | `hello.o` |
| 실행 파일 | `hello.exe` | `hello` (확장자 없이 쓰는 경우가 많다) |

Unix 계열에서 GCC에 출력 파일 이름을 지정하지 않으면 실행 파일은 `a.out`이라는 이름으로 만들어진다. Windows용 GCC에서는 보통 `a.exe`가 된다. 이처럼 이름을 붙이는 방식도 도구와 환경에 따라 다르다.

### 도구마다 맡은 일이 다르다

앞 절의 단계를 사람이 직접 하나씩 실행하는 대신, 여러 도구가 나누어 맡는다.

| 도구 | 하는 일 | 이 책에서 쓰는 예 |
|---|---|---|
| 편집기(editor) | 소스 파일을 작성하고 저장한다 | Visual Studio의 코드 편집기 |
| 컴파일러 도구 모음 | 전처리·컴파일·어셈블을 수행하여 목적 파일을 만든다 | MSVC, GCC |
| 링커(linker) | 목적 파일과 라이브러리를 연결하여 실행 파일을 만든다 | MSVC와 GCC에 포함된 링커 |
| 디버거(debugger) | 실행 중인 프로그램을 멈추고 상태를 살펴보게 한다 | Visual Studio 디버거 |
| 통합 개발 환경(IDE) | 위 도구들을 한 화면에서 사용하게 묶어 준다 | Visual Studio 2022 |

**통합 개발 환경(IDE, Integrated Development Environment)**은 편집, 빌드, 실행, 디버깅을 한곳에서 할 수 있게 해 주는 프로그램이다. 여기서 중요한 구별이 있다. **Visual Studio는 IDE이고, 그 안에서 실제로 C 소스를 번역하는 컴파일러 도구 모음은 MSVC(Microsoft C/C++ 컴파일러)다.** Visual Studio의 빌드 메뉴를 누르면 Visual Studio가 MSVC의 컴파일러와 링커를 대신 실행해 준다.

**GCC(GNU Compiler Collection)**도 컴파일러 도구 모음이다. GCC는 주로 터미널에서 명령어로 실행하며, 여러 IDE와 편집기에서도 GCC를 빌드 도구로 사용할 수 있다. 이름이 비슷한 Visual Studio Code는 Visual Studio와 다른 프로그램이다. Visual Studio Code는 편집기이며, C 프로그램을 빌드하려면 컴파일러를 따로 설치하고 연결해야 한다.

```text
┌──────────────── 통합 개발 환경 (예: Visual Studio) ────────────────┐
│                                                                    │
│   편집기  →  빌드 명령  →  [ 컴파일러 도구 모음 → 링커 ]  →  실행/디버거  │
│              (메뉴·단축키)        (예: MSVC)                           │
└────────────────────────────────────────────────────────────────────┘
```

### 디버거와 새니타이저는 이름만 알아 두자

**디버거(debugger)**는 실행 중인 프로그램을 원하는 위치에서 멈추고, 한 줄씩 진행하면서 값이 어떻게 바뀌는지 살펴보게 해 주는 도구다. 프로그램이 왜 기대와 다르게 동작하는지 찾을 때 쓴다. 조건문과 반복문을 배운 뒤 Chapter 7에서 기본 사용법을 익힌다.

**새니타이저(sanitizer)**는 빌드할 때 검사 코드를 함께 넣어, 실행 중에 특정 종류의 잘못된 메모리 사용 등을 발견하면 알려 주는 도구다. 예를 들어 MSVC와 GCC는 모두 AddressSanitizer라는 새니타이저를 지원한다. 포인터와 메모리를 다루는 뒷부분에서 필요할 때 소개한다.

### 설치할 때 확인할 것

Visual Studio 2022를 설치할 때는 워크로드 목록에서 **‘C++를 사용한 데스크톱 개발’**을 선택한다. 이름에는 C++만 적혀 있지만, 이 워크로드에 MSVC 컴파일러와 링커가 들어 있고 MSVC는 C 소스도 컴파일한다. 다만 이것은 **같은 도구 모음이 두 언어를 모두 처리한다**는 뜻이지, C와 C++가 같은 언어라는 뜻은 아니다. 이 점은 다음 절에서 다시 확인한다.

이 절에서는 Visual Studio 2022에서 C 프로그램을 만드는 최소한의 작업 흐름을 정리한다. 메뉴와 대화 상자의 이름이나 위치는 Visual Studio의 버전, 업데이트, 표시 언어에 따라 조금씩 다를 수 있다. 이름이 정확히 같지 않더라도 **무엇을 하려는 단계인지**를 기준으로 찾으면 된다.

### 솔루션과 프로젝트

Visual Studio는 파일을 **프로젝트(project)** 단위로 관리한다. 프로젝트는 실행 파일 하나를 만드는 데 필요한 소스 파일과 설정을 담는 단위이고, **솔루션(solution)**은 하나 이상의 프로젝트를 묶는 단위다. 이 책의 예제는 당분간 솔루션 하나에 프로젝트 하나로 충분하다. 새 프로젝트를 만들면 솔루션도 함께 만들어진다.

### 1단계: 빈 프로젝트 만들기

1. **파일 → 새로 만들기 → 프로젝트**를 선택한다.
2. 템플릿 목록에서 **빈 프로젝트**를 선택한다. 템플릿 설명에 C++라고 표시되어도 괜찮다. 어떤 언어로 컴파일할지는 다음 단계에서 추가할 소스 파일이 정한다.
3. 프로젝트 이름(예: `hello`)과 저장 위치를 정하고 **만들기**를 누른다.

### 2단계: `.c` 소스 파일 추가하기

1. 오른쪽의 **솔루션 탐색기**에서 **소스 파일** 폴더를 마우스 오른쪽 버튼으로 누르고 **추가 → 새 항목**을 선택한다.
2. 항목 목록에는 C++ 파일(`.cpp`)만 보일 수 있다. 그래도 파일 이름 칸에 **확장자까지 포함하여 `hello.c`**라고 직접 입력한 뒤 **추가**를 누른다.
3. 솔루션 탐색기에서 파일 이름이 `hello.c`로 끝나는지 반드시 확인한다.

### `.c`와 `.cpp`는 왜 중요한가?

<!-- SOURCE: [E7] MSVC: 기본적으로 .c는 C, .cpp/.cxx는 C++로 컴파일; [E8] "C와 C++는 비슷하지만 같지 않다".
검증: `int class = 0;` 예 — MSVC .c(/std:c17 /W4) 통과, .cpp 오류 C2236 등; GCC -std=c17 통과, g++ 오류.
ROLE: 추가 (04:C8 REQUIRED BOX). -->

> **확장자가 언어를 정한다**
>
> MSVC는 별도로 지정하지 않으면 확장자가 `.c`인 파일은 **C**로, `.cpp`인 파일은 **C++**로 컴파일한다. 파일 이름을 `hello.cpp`로 만들면, 내용이 C처럼 보여도 실제로는 C++의 규칙으로 검사된다.
>
> C와 C++는 비슷한 부분이 많지만 서로 다른 언어다. C에서 올바른 코드가 C++에서는 오류가 되기도 하고, 그 반대도 있다. 예를 들어 C에서는 `class`라는 단어를 보통의 이름으로 쓸 수 있지만, C++에서 `class`는 특별한 뜻을 가진 예약어이므로 같은 코드가 오류가 된다. 두 언어에서 모두 받아들여지는 코드라도 세부 규칙이 다른 경우가 있다.
>
> 따라서 C를 배우는 동안에는 **모든 소스 파일의 확장자가 `.c`인지** 확인해야 한다. 이미 `.cpp`로 만들었다면 솔루션 탐색기에서 파일 이름을 `.c`로 바꾼다. 프로젝트 설정으로 언어를 강제하는 방법도 있지만, 이 책에서는 확장자로 구분하는 방법을 기본으로 한다.

### 3단계: C17 표준과 경고 수준 설정하기

소스 파일을 추가한 뒤에는 프로젝트 속성에서 두 가지를 설정한다. 프로젝트에 소스 파일이 하나도 없으면 C/C++ 관련 속성 항목이 보이지 않을 수 있으므로, 2단계를 먼저 마친다.

1. 솔루션 탐색기에서 프로젝트 이름을 마우스 오른쪽 버튼으로 누르고 **속성**을 선택한다.
2. 위쪽의 **구성**은 ‘모든 구성’, **플랫폼**은 ‘모든 플랫폼’으로 바꾼다. 그래야 디버그용과 배포용 설정에 모두 적용된다.
3. **구성 속성 → C/C++ → 일반 → 경고 수준**을 **수준4(/W4)**로 바꾼다.
4. **구성 속성 → C/C++ → 언어 → C 언어 표준**을 **ISO C17(2018) 표준(/std:c17)**으로 바꾼다.
5. **확인**을 누른다.

Visual Studio의 새 프로젝트는 경고 수준이 **수준3(/W3)**으로 시작한다. 그대로 두면 이 책에서 기대하는 경고 일부가 표시되지 않는다. 두 설정이 무엇을 뜻하는지는 2.5절에서 설명한다.

### 4단계: 빌드하기

**빌드 → 솔루션 빌드**를 선택한다(단축키 `Ctrl+Shift+B`). 저장하지 않은 소스 파일은 빌드 전에 자동으로 저장된다.

- **출력** 창에는 빌드 과정과 결과가 표시된다. 성공하면 성공한 프로젝트 수가 1, 실패한 프로젝트 수가 0으로 나타난다.
- **오류 목록** 창에는 오류와 경고가 표 형태로 정리된다. 항목을 두 번 누르면 편집기에서 해당 줄로 이동한다.

오류 목록에는 빌드할 때 나온 진단과, 입력하는 동안 편집기가 미리 분석한 진단(IntelliSense)이 함께 표시될 수 있다. 둘이 다르게 보일 때는 **빌드 결과**를 기준으로 판단한다. 오류 목록 위쪽의 필터에서 ‘빌드 전용’을 고르면 빌드 결과만 볼 수 있다.

### 5단계: 실행하기

**디버그 → 디버그하지 않고 시작**을 선택한다(단축키 `Ctrl+F5`). 필요하면 먼저 빌드한 뒤, 콘솔 창을 열어 프로그램을 실행한다.

프로그램이 끝난 뒤 콘솔 창에 “창을 닫으려면 아무 키나 누르세요” 같은 안내가 나타날 수 있다. 이 문구는 **Visual Studio가 덧붙인 안내이며, 우리 프로그램의 출력이 아니다.**

**디버그 → 디버깅 시작**(`F5`)은 프로그램을 디버거와 함께 실행한다. 디버거를 쓰는 방법을 배우기 전까지는 `Ctrl+F5`로 실행하는 편이 결과를 확인하기 쉽다.

빌드가 끝난 실행 파일은 솔루션 폴더 아래의 출력 폴더에 만들어진다. 폴더 이름은 구성과 플랫폼에 따라 달라지며, 예를 들어 `x64\Debug` 같은 폴더에 `hello.exe`가 생긴다.

### 언어 표준이란

C 언어의 규칙은 국제 표준(ISO/IEC 9899)으로 정해져 있고, 시간이 흐르며 여러 번 개정되었다. 컴파일러는 이 표준을 바탕으로 만들어지지만, 어느 개정판의 규칙을 따를지, 표준에 없는 확장 기능을 얼마나 허용할지는 컴파일러와 설정에 따라 다르다. 같은 소스를 같은 규칙으로 검사받으려면 **어떤 표준을 기준으로 할지 도구에 알려 주어야** 한다.

> **짧게 보는 C 표준의 흐름**
>
> | 흔히 부르는 이름 | 특징 |
> |---|---|
> | C89 / C90 | 처음으로 표준화된 C |
> | C99 | `//` 주석 등 여러 기능 추가 |
> | C11 | 기능 추가와 정리 |
> | C17 | C11의 오류를 바로잡은 개정판(2018년 발행) |
> | C23 | 가장 최근 개정판 |
>
> 이 책은 **C17**을 기준으로 삼는다. C23에서 달라진 점은 필요한 곳에서만 짧게 언급한다.

### 표준 모드를 정하는 옵션

| 도구 모음 | C17 모드 옵션 | 지정하지 않았을 때 |
|---|---|---|
| MSVC | `/std:c17` | C89를 바탕으로 Microsoft 확장 기능을 더한 방식으로 C를 컴파일한다 |
| GCC | `-std=c17` | 버전마다 기본값이 다르며, 표준에 GNU 확장 기능을 더한 방식이 기본이다 |

이 옵션들은 **C 언어의 문법이 아니라 도구 모음의 설정**이다. 소스 파일 안에 쓰는 것이 아니라, Visual Studio의 프로젝트 속성이나 명령줄에서 컴파일러에게 전달한다. 옵션을 명시해 두면 컴파일러의 기본값이 바뀌어도 같은 기준으로 빌드할 수 있다.

다만 표준 모드를 지정했다고 해서 표준에 맞지 않는 코드가 모두 걸러지는 것은 아니다. 표준 모드는 **어떤 규칙을 기준으로 삼을지** 정하는 설정이고, 코드가 이식성 있게 작성되었는지는 경고를 읽고 두 도구 모음에서 확인하는 습관으로 보완한다.

### 경고 수준을 정하는 옵션

| 도구 모음 | 이 책의 설정 | 의미 |
|---|---|---|
| MSVC | `/W4` | 경고 수준 1~4의 경고를 표시한다. Microsoft도 새 프로젝트에 권장하는 수준이다 |
| GCC | `-Wall -Wextra` | `-Wall`이 켜는 경고에 `-Wextra`가 켜는 추가 경고를 더한다 |

`-Wall`의 all은 ‘모든 경고’라는 뜻이 아니다. GCC 문서도 `-Wall`이 켜지 않는 경고가 있다고 밝히고 있다. 그래서 이 책은 `-Wextra`를 함께 쓴다. MSVC의 기본 경고 수준은 IDE에서 `/W3`, 명령줄에서 `/W1`이므로 `/W4`는 직접 지정해야 한다.

### 명령줄에서 빌드하는 경우

같은 소스 파일을 두 도구 모음으로 빌드하는 명령은 다음과 같다. `$`나 `>` 같은 프롬프트 기호는 입력하지 않는다.

```text
MSVC (Visual Studio의 ‘개발자 명령 프롬프트’에서)
    cl /std:c17 /W4 hello.c

GCC
    gcc -std=c17 -Wall -Wextra hello.c -o hello
```

MSVC의 `cl` 명령은 일반 명령 프롬프트에서는 바로 실행되지 않을 수 있다. Visual Studio와 함께 설치되는 **개발자 명령 프롬프트**를 사용해야 컴파일러와 라이브러리의 위치가 올바르게 설정된다. GCC의 `-o hello`는 만들어질 실행 파일의 이름을 정하는 옵션이다.

이처럼 **같은 표준 C 소스를 서로 다른 도구 모음으로 빌드하는 것**은 이식성의 간단한 예다. 이식성 있게 작성한 소스 코드는 다른 환경으로 옮겨 다시 빌드하기 쉽지만, 모든 C 프로그램이 어디서나 수정 없이 동작한다는 보장은 아니다. 이 책의 예제는 두 도구 모음에서 모두 경고 없이 빌드되는 것을 원칙으로 한다.

> **경고를 오류로 바꾸는 옵션**
>
> MSVC의 `/WX`와 GCC의 `-Werror`는 경고가 하나라도 있으면 빌드를 실패로 처리한다. 경고를 확실히 놓치지 않게 해 주는 설정이지만, 지금은 사용하지 않아도 된다. 개발 도구를 정리하는 부록 A에서 다시 소개한다.

### 오류와 경고

빌드하는 동안 도구 모음은 두 종류의 진단 메시지를 낸다.

- **오류(error):** 규칙 위반이나 연결 실패 때문에 현재 빌드가 목표한 결과물을 정상적으로 만들거나 갱신하지 못했다는 뜻이다. 이전에 성공한 빌드의 실행 파일은 디스크에 남아 있을 수 있다.
- **경고(warning):** 빌드는 계속할 수 있지만, 실수이거나 위험할 가능성이 있는 코드를 발견했다는 뜻이다.

경고만 있고 빌드가 성공하면 실행 파일은 만들어진다. 그래서 경고를 무시하기 쉽지만, 경고는 **아직 오류가 드러나지 않았을 뿐인 문제**를 가리키는 경우가 많다. 경고가 나타나면 그 원인을 이해하고, 가능하면 코드를 고쳐서 경고가 사라지게 하자. 원인을 모르는 채 경고를 끄는 것은 해결이 아니다.

> **빌드에 실패했는데 프로그램이 실행된다면**
>
> 빌드에 실패했는데도 실행 명령을 고르면, Visual Studio가 **마지막으로 성공한 빌드를 실행할지** 묻는 경우가 있다. 이때 실행하면 방금 고친 코드가 아니라 예전에 만들어진 실행 파일이 실행된다. 수정한 내용을 확인하려는 것이라면 실행하지 말고 오류부터 고친다.

### 문제의 네 가지 종류

프로그램의 문제는 **언제, 어느 단계에서 드러나는가**에 따라 다음과 같이 나눌 수 있다.

| 종류 | 드러나는 때 | 확인 방법 | 예 |
|---|---|---|---|
| 컴파일 단계 문제 | 빌드 중, 컴파일할 때 | 컴파일러 진단 확인 | 세미콜론 누락, 짝이 맞지 않는 괄호나 따옴표, 잘못 쓴 단어 |
| 링크 문제 | 빌드 중, 링크할 때 | 링커 진단 확인 | 사용한 이름의 정의를 찾을 수 없음 |
| 실행 중 문제 | 빌드는 성공했지만 실행 중 정상적인 진행·완료에 실패 | 프로그램·운영체제·실행 환경의 메시지나 실행 상태 확인 | 필요한 파일을 열 수 없어 작업 불가, 예기치 않은 종료 |
| 논리 문제 | 빌드와 실행은 끝났지만 결과나 동작이 의도와 다름 | 기대한 결과·동작과 비교 | 평균 대신 합계를 출력함 |

**컴파일 단계 문제**는 소스가 언어 규칙이나 도구의 설정에 맞지 않아 컴파일을 정상적으로 마칠 수 없는 경우다.

**링크 문제**는 컴파일이 끝난 뒤에 생긴다. 예를 들어 사용한다고 알린 기능의 실제 정의가 어디에도 없거나, 라이브러리 함수의 이름을 잘못 적으면 링커가 그 이름을 연결하지 못한다. MSVC는 이런 경우를 `LNK`로 시작하는 오류 번호로, GCC 환경의 링커는 `undefined reference`라는 문구로 알린다. 다만 같은 실수라도 도구 모음과 버전에 따라 컴파일 단계에서 먼저 오류로 멈추기도 한다. 2.7절의 실험에서 그 예를 볼 수 있다.

**실행 중 문제**는 빌드가 성공하고 실행이 시작된 뒤, 문제가 생겨 정상적으로 계속 진행하거나 작업을 끝내지 못하는 경우다. 필요한 파일을 열 수 없어 작업을 수행하지 못하거나, 실행이 예기치 않게 끝나는 경우가 그 예다. 반드시 프로그램이 비정상 종료되는 것은 아니다. 오류 메시지를 표시하고 해당 작업을 중단할 수도 있다.

**논리 문제**는 빌드와 실행은 끝났지만 결과나 동작이 의도한 것과 다른 경우다. 평균 대신 합계를 출력하는 것이 그 예다. 컴파일러와 링커는 규칙과 연결을 확인할 뿐, 의도한 결과까지 판단하지는 못한다. Chapter 1에서 강조했듯이 **실행 전에 기대하는 결과를 정해 두고 비교하는 습관**이 논리 문제를 찾는 첫걸음이다.

```text
빌드했을 때
 ├─ 컴파일 단계에서 멈췄다 ───→ 컴파일 단계 문제: 보고된 줄과 그 앞줄의 표기를 확인
 ├─ 링크 단계에서 멈췄다 ─────→ 링크 문제: 사용한 이름의 철자와 정의가 있는지 확인
 └─ 빌드에 성공했다 → 실행했을 때
        ├─ 실행 중 문제가 생겨 작업을 진행·완료하지 못했다 ──→ 실행 중 문제
        └─ 끝까지 실행되었다 → 결과와 동작을 의도한 것과 비교
               ├─ 다르다 ──→ 논리 문제: 절차와 코드를 다시 추적
               └─ 같다 ───→ 다른 입력으로도 확인
```

### 진단 메시지의 구성

진단 메시지에는 보통 **파일 이름, 줄 번호, 오류인지 경고인지, 식별 번호, 설명**이 들어 있다. 같은 문제라도 도구 모음마다 형식이 다르다. 다음은 2.7절의 실험에서 실제로 얻은 메시지다.

```text
MSVC:  nosemi.c(6): error C2143: 구문 오류: ';'이(가) 'return' 앞에 없습니다.
GCC:   nosemi.c:5:26: error: expected ';' before 'return'
```

MSVC의 메시지는 `파일(줄): error 번호: 설명` 형식이고, GCC의 메시지는 `파일:줄:열: error: 설명` 형식이다. MSVC의 `C2143`, `LNK2019` 같은 번호로 Microsoft 문서를 검색하면 해당 진단에 대한 설명을 찾을 수 있다.

두 메시지가 가리키는 줄 번호가 다르다는 점에도 주목하자. 이 예에서 실제로 빠진 세미콜론은 5번 줄 끝에 있어야 한다. 그런데 컴파일러는 다음 줄의 `return`을 읽고 나서야 문제를 확신할 수 있으므로, MSVC는 6번 줄을 보고했다. **보고된 줄에 잘못이 없어 보이면 바로 앞줄을 살펴보자.**

### 첫 번째 의미 있는 오류부터 고친다

작은 실수 하나 때문에 오류가 수십 개 나타날 수 있다. 첫 번째 실수 때문에 컴파일러가 그 뒤의 코드를 잘못 해석하면, 원래는 문제가 없는 부분까지 오류로 보고하기 때문이다.

따라서 오류가 많을 때는 다음 순서를 따른다.

1. 목록의 **맨 위에서부터** 읽고, 처음으로 뜻이 분명한 오류를 찾는다.
2. 그 오류 하나를 고친다.
3. **다시 빌드한다.** 뒤따르던 오류가 함께 사라지는 경우가 많다.
4. 남은 오류에 대해 같은 과정을 반복한다.

목록의 아래쪽에 있는 오류부터 고치려 하면, 실제로는 문제가 없는 코드를 잘못 수정하게 될 수 있다.

### 소스 입력하기

2.4절의 방법으로 만든 `hello.c`에 다음 내용을 입력한다.

> **이 예제에 대하여**
>
> 지금은 구조를 외우거나 이해할 필요가 없으며, 실행 흐름을 확인하기 위한 예제다. 각 줄의 의미는 Chapter 3에서 설명한다.

```c
#include <stdio.h>

int main(void)
{
    printf("Hello, C!\n");
    return 0;
}
```

입력할 때는 보이는 그대로, 대소문자와 기호까지 똑같이 적는다. C는 대문자와 소문자를 다른 글자로 취급하며, 괄호·중괄호·따옴표·세미콜론 가운데 하나만 빠져도 빌드에 실패한다. 줄 앞의 들여쓰기는 읽기 쉽게 하려는 것이므로 공백 개수가 조금 달라도 괜찮다.

### Visual Studio에서 빌드하고 실행하기

1. **빌드 → 솔루션 빌드**를 선택하고, 출력 창에서 빌드가 성공했는지 확인한다.
2. 오류 목록에 오류나 경고가 없는지 확인한다.
3. **디버그 → 디버그하지 않고 시작**으로 실행한다.

콘솔 창에 다음이 표시되면 성공이다.

```text
Hello, C!
```

그 아래에 나타나는 “아무 키나 누르세요” 같은 안내는 앞에서 말했듯이 Visual Studio가 덧붙인 것이다.

### GCC로 빌드하고 실행하기

GCC가 설치된 환경에서는 `hello.c`가 있는 폴더에서 다음 명령으로 빌드하고 실행한다.

```text
빌드
    gcc -std=c17 -Wall -Wextra hello.c -o hello

실행 (Unix 계열 셸)
    ./hello

실행 (Windows 명령 프롬프트 또는 PowerShell)
    .\hello
```

빌드 명령이 아무것도 출력하지 않고 끝나면 오류와 경고 없이 성공한 것이다. 실행하면 Visual Studio에서와 같이 `Hello, C!`가 출력된다. 같은 소스가 서로 다른 도구 모음과 실행 방법을 거쳐 같은 결과를 낸 것이다.

### 일부러 문제를 만들어 보기

진단 메시지는 미리 경험해 두면 실제로 만났을 때 당황하지 않는다. 다음 실험을 하나씩 해 보고, 실험이 끝날 때마다 소스를 원래대로 되돌린다.

**실험 1: 세미콜론 지우기 (컴파일 단계 문제)**

`printf`로 시작하는 줄의 끝에 있는 `;`를 지우고 빌드한다. 빌드는 컴파일 단계에서 실패한다. 2.6절에서 본 것처럼 MSVC는 다음 줄인 `return` 줄을, GCC는 세미콜론이 빠진 줄의 끝을 가리킨다. 어느 쪽이든 **보고된 위치와 그 앞을 함께 살펴보면** 원인을 찾을 수 있다.

**실험 2: 함수 이름의 철자 바꾸기 (같은 실수, 다른 단계)**

`printf`를 `prinft`로 잘못 적고 빌드한다. 이번에는 도구 모음에 따라 결과가 다르다.

| 도구 모음 | 진단 | 멈춘 단계 |
|---|---|---|
| MSVC | 경고 `C4013`(정의되지 않은 이름) 뒤에 오류 `LNK2019`, `LNK1120` | 컴파일은 경고와 함께 통과, **링크에서 실패** |
| GCC 16 | `implicit declaration of function 'prinft'` 오류와 함께 `printf`를 제안 | **컴파일에서 실패** |

MSVC에서는 컴파일러가 이름이 이상하다고 **경고**만 한 채 목적 파일을 만들고, 링커가 그 이름의 정의를 라이브러리에서 찾지 못해 실패했다. 최근 GCC는 같은 상황을 컴파일 단계에서 오류로 처리한다. 두 경우 모두 이번 수정 내용을 반영한 실행 파일을 만들지 못한다. 이 실험은 **경고가 실제 문제의 첫 단서였다**는 점과, 문제를 잡아내는 단계가 도구 모음에 따라 다를 수 있다는 점을 보여 준다.

**실험 3: 출력할 글자 바꾸기 (논리 문제)**

`Hello, C!`를 `Helo, C!`로 바꾸고 빌드하고 실행한다. 빌드도 실행도 문제없이 끝나고 `Helo, C!`가 출력된다. 도구는 아무것도 알려 주지 않았지만, 결과는 우리가 원한 것과 다르다. 기대한 결과를 미리 알고 있었기 때문에 이 차이를 발견할 수 있다.

> **선택 읽기: GCC로 빌드 단계를 하나씩 확인하기**
>
> GCC는 옵션으로 빌드를 원하는 단계에서 멈출 수 있어, 2.2절의 단계를 눈으로 확인해 볼 수 있다.
>
> ```text
> gcc -std=c17 -E hello.c -o hello.i    전처리까지 (전처리된 소스)
> gcc -std=c17 -S hello.c -o hello.s    컴파일까지 (어셈블리 코드)
> gcc -std=c17 -c hello.c -o hello.o    어셈블까지 (목적 파일)
> gcc hello.o -o hello                  링크 (실행 파일)
> ```
>
> 전처리 결과인 `hello.i`를 열어 보면, 몇 줄짜리 소스가 천 줄이 넘게 늘어나 있다. `#include`가 가져온 파일의 내용이 모두 그 자리에 들어갔기 때문이다. 정확한 크기는 환경에 따라 다르다. MSVC는 이런 중간 파일을 기본적으로 따로 보여 주지 않지만, 개념적인 단계는 같다.

| `.obj`, `.exe` 같은 확장자는 C 언어의 규칙이다. | 운영체제와 도구 모음의 관례다. Unix 계열에서는 `.o`를 쓰고 실행 파일에 확장자를 붙이지 않는 경우가 많다. |

## 핵심 정리

<!-- SOURCE: [T] Ch02; [K] §1.1; [E1], [E3]-[E12]. ROLE: 기본. -->

- 프로그램 개발의 구현 단계에서는 **작성 → 빌드 → 실행 → 확인**의 순환을 반복한다. 소스 파일은 프로그램의 원본이므로 반드시 보관한다.
- 빌드는 **전처리 → 컴파일 → 어셈블 → 링크**로 이루어진 전체 과정이며, 컴파일은 그중 한 단계다. 도구 모음에 따라 몇 단계가 합쳐지거나 중간 파일이 보이지 않을 수 있다.
- 전처리기는 `#`으로 시작하는 지시문을 처리하고, 컴파일러는 언어 규칙을 검사하고 번역하며, 어셈블러는 목적 파일을 만들고, 링커는 목적 파일과 라이브러리를 연결하여 실행 파일을 만든다.
- Visual Studio는 IDE이고 MSVC와 GCC는 컴파일러 도구 모음이다. MSVC는 기본적으로 `.c` 파일을 C로, `.cpp` 파일을 C++로 컴파일하므로 C 소스 파일은 `.c`로 만든다.
- 이 책은 C17을 기준으로 MSVC에서는 `/std:c17 /W4`, GCC에서는 `-std=c17 -Wall -Wextra`를 사용한다. 이 옵션들은 C 문법이 아니라 도구 모음의 설정이다.
- 오류는 현재 빌드를 실패하게 하며, 경고는 보통 빌드를 멈추지 않지만 조사해야 할 신호다. 문제는 컴파일 단계, 링크, 실행 중, 논리 문제로 나눌 수 있다.
- 오류가 많으면 첫 번째 의미 있는 오류부터 고치고 다시 빌드한다. 보고된 줄에 잘못이 없어 보이면 앞줄을 확인한다.

### 1. 빌드 단계 순서 정하기

다음 항목을 소스 파일에서 프로그램 실행까지의 순서로 배열하고, 각 단계가 끝났을 때 만들어지는 것을 적어라.

- 가. 어셈블
- 나. 실행
- 다. 링크
- 라. 전처리
- 마. 컴파일

Visual Studio에서 빌드할 때 이 단계 가운데 어셈블리 코드 파일이 따로 보이지 않는 이유도 한 문장으로 설명하라.

### 2. 도구의 역할 구별하기

다음 설명에 맞는 것을 보기에서 골라라. 한 보기를 여러 번 고를 수도 있다.

보기: Visual Studio, MSVC, GCC, 링커, 디버거, 편집기

1. 소스 파일을 작성하고 저장하는 데 쓴다.
2. 편집·빌드·실행·디버깅을 한 화면에서 할 수 있게 묶어 준다.
3. C 소스를 규칙에 따라 검사하고 목적 파일로 번역한다. (두 가지)
4. 목적 파일과 라이브러리를 연결하여 실행 파일을 만든다.
5. 실행 중인 프로그램을 멈추고 상태를 살펴보게 해 준다.

그리고 “Visual Studio를 설치했으니 C 컴파일러를 설치한 것과 같다”라는 말이 어떤 조건에서 맞고, 어떤 점에서 부정확한지 설명하라.

### 3. 문제의 종류 판단하기

다음 상황을 컴파일 단계 문제, 링크 문제, 실행 중 문제, 논리 문제 가운데 하나로 분류하고 이유를 적어라.

1. 빌드 결과에 `error C2143`이 표시되고 이번 빌드가 실패했다.
2. 컴파일은 끝났지만 `undefined reference`라는 메시지와 함께 이번 빌드가 실패했다.
3. 평균을 구하는 프로그램이 문제없이 끝났는데, 세 값의 평균 대신 합계를 출력했다.
4. 빌드는 성공했는데, 특정 값을 입력하면 프로그램이 결과를 내지 못하고 도중에 끝나 버린다.
5. `Hello, C!`를 출력해야 하는 프로그램이 `hello, c!`를 출력했다.

### 4. `.c`와 `.cpp`

친구가 Visual Studio에서 새 항목을 추가하면서 이름을 바꾸지 않아 `Source.cpp`라는 파일에 C 코드를 작성했다.

1. 이 파일은 어떤 언어의 규칙으로 컴파일되는가?
2. “지금은 오류 없이 빌드되니 상관없다”라는 친구의 말이 왜 충분한 이유가 되지 못하는지 설명하라.
3. Visual Studio에서 이 문제를 확인하고 바로잡는 방법을 적어라.

### 5. 옵션 고르기

1. 다음 표의 빈칸을 채워라.

   | 목적 | MSVC | GCC |
   |---|---|---|
   | C17 표준 모드 | (가) | (나) |
   | 이 책의 경고 설정 | (다) | (라) |

2. 다음 명령과 설명 가운데 잘못된 것을 모두 찾고 바르게 고쳐라.
   - `gcc /std:c17 /W4 hello.c -o hello`
   - `cl -std=c17 -Wall -Wextra hello.c`
   - “`-Wall`을 쓰면 GCC가 알고 있는 모든 경고가 켜진다.”
   - “Visual Studio의 새 프로젝트는 처음부터 경고 수준이 `/W4`로 설정되어 있다.”

### 6. 진단 메시지 해석하기

같은 소스 파일을 두 도구 모음으로 빌드했더니 다음 메시지가 나왔다.

```text
report.c(12): error C2143: 구문 오류: ';'이(가) 'return' 앞에 없습니다.
report.c:11:30: error: expected ';' before 'return'
```

1. 각 메시지는 어느 도구 모음의 것인가? 형식의 차이를 근거로 들어라.
2. 두 메시지가 가리키는 줄 번호가 다른 이유를 설명하라.
3. 실제로 고쳐야 할 곳은 어디일 가능성이 가장 높은가?

### 7. 오류가 많을 때의 작업 순서

처음 빌드한 프로그램에서 오류가 23개 표시되었다. 목록의 맨 아래 오류는 뜻을 이해하기 어렵고, 맨 위 오류는 “괄호가 필요합니다”라는 내용이다.

1. 어떤 순서로 작업해야 하는지 단계별로 적어라.
2. 오류를 하나 고친 뒤 곧바로 다시 빌드하는 것이 왜 효율적인지 설명하라.
3. 오류가 남은 상태에서 실행을 선택했더니 “마지막으로 성공한 빌드를 실행할까요?”라는 질문이 나왔다. 어떻게 답해야 하며, 그 이유는 무엇인가?

### 8. 파이프라인 추적하기 〔심화·도전〕

> **심화·도전 문제:** 1~7번보다 한 단계 어려운 문제다. 처음에 풀지 못하더라도 다음 장을 공부하는 데는 지장이 없다.

어떤 프로그램이 두 소스 파일 `calc.c`와 `report.c`로 이루어져 있고, Windows에서 MSVC로 빌드한다.

1. 처음 빌드할 때 만들어지는 목적 파일과 실행 파일의 이름을 예상하여, 소스 파일에서 실행 파일까지의 흐름을 그림으로 그려라. 파일 이름은 환경의 관례를 따른다고 가정한다.
2. `report.c`만 고친 뒤 다시 빌드할 때, 반드시 다시 수행해야 하는 단계와 생략할 수 있는 단계를 구별하라.
3. 완성된 실행 파일을 Unix 계열 운영체제의 친구에게 보냈더니 실행되지 않았다. 친구가 이 프로그램을 쓰려면 무엇을 받아서 어떻게 해야 하는지 설명하라.

> **풀이 힌트:** 1번에서는 중간 결과가 모든 도구에서 파일로 보이는 것은 아니라는 점을 떠올리자. 3번은 각 단계에서 어느 도구가 문제를 발견하는지 생각하면 된다. 5번은 두 도구 모음의 옵션 표기 방식이 다르다는 점과 IDE의 기본 경고 수준에 주의한다. 6번은 컴파일러가 세미콜론이 빠졌다는 사실을 언제 확신할 수 있는지 생각해 보자. 8번의 2번은 목적 파일이 소스 파일마다 따로 만들어진다는 점에서 출발한다.
>
