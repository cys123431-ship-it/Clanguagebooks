# Chapter 2. 프로그램 작성 과정과 개발 도구 — 정답과 상세해설

> 본 문서는 Chapter 2 승인 원고의 확인 문제에 대한 별도 정답·해설이다.

## 문제 1. 빌드 단계 순서 정하기

### 정답

제시된 항목의 올바른 순서는 다음과 같다.

**라 → 마 → 가 → 다 → 나**

즉,

**전처리 → 컴파일 → 어셈블 → 링크 → 실행**

순서다.

| 단계 | 제시된 글자 | 개념적으로 얻는 결과 |
|---|---|---|
| 전처리 | 라 | 전처리된 소스 |
| 컴파일 | 마 | 어셈블리 수준의 표현 또는 그에 해당하는 더 낮은 수준의 중간 표현 |
| 어셈블 | 가 | 목적 파일(object file) |
| 링크 | 다 | 실행 파일(executable) |
| 실행 | 나 | 운영체제가 실행 파일을 적재하고 프로그램을 시작한다. |

Visual Studio에서 어셈블리 코드 파일이 따로 보이지 않는 것은 **어셈블 단계가 없어서가 아니다.** 실제 도구 모음은 여러 단계를 내부에서 이어서 처리할 수 있고, 어셈블리 수준의 중간 결과를 별도 파일로 저장하지 않을 수도 있기 때문이다.

### 상세해설

전처리 단계에서는 컴파일 전에 필요한 지시문을 처리하여 컴파일러가 읽을 소스를 준비한다. 컴파일 단계에서는 C 언어 규칙을 검사하고 더 낮은 수준의 표현으로 번역한다. 어셈블 단계에서는 그 표현을 기계어 코드가 들어 있는 목적 파일로 만든다. 링크 단계에서는 목적 파일과 필요한 라이브러리를 연결하여 실행 파일을 만든다. 마지막 실행 단계에서는 운영체제가 그 실행 파일을 적재하고 프로그램을 시작한다.

이 순서는 **개념적인 빌드 모델**이다. 모든 구현이 각 단계의 결과를 실제 파일로 하나씩 저장한다는 뜻은 아니다. 따라서 중간 파일이 보이지 않는 것과 단계 자체가 존재하지 않는 것은 구별해야 한다.

## 문제 2. 도구의 역할 구별하기

### 정답

1. **편집기**
2. **Visual Studio**
3. **MSVC, GCC**
4. **링커**
5. **디버거**

### 상세해설

| 항목 | 역할 |
|---|---|
| 편집기 | 소스 파일을 작성하고 저장한다. |
| Visual Studio | 편집·빌드·실행·디버깅 도구를 한 환경에서 사용할 수 있게 묶어 주는 IDE다. |
| MSVC, GCC | C 소스를 검사하고 번역하여 목적 파일을 만드는 컴파일러 도구 모음이다. |
| 링커 | 목적 파일과 라이브러리를 연결하여 실행 파일을 만든다. |
| 디버거 | 실행 중인 프로그램을 멈추고 상태를 살펴보게 한다. |

“Visual Studio를 설치했으니 C 컴파일러를 설치한 것과 같다”라는 말은 **필요한 C/C++ 개발 워크로드와 구성 요소까지 함께 설치한 경우에는 실무적으로 비슷하게 느껴질 수 있지만, 기술적으로는 정확하지 않다.**

Visual Studio 자체는 **IDE**다. 실제 C 컴파일러 도구 모음은 **MSVC**이며, Visual Studio 설치 과정에서 ‘C++를 사용한 데스크톱 개발’ 같은 적절한 워크로드를 선택했을 때 MSVC가 구성 요소로 함께 설치된다. 따라서 모든 Visual Studio 설치에 MSVC가 반드시 들어 있다고 가정하면 안 된다.

## 문제 3. 문제의 종류 판단하기

### 정답

| 번호 | 분류 | 이유 |
|---:|---|---|
| 1 | **컴파일 단계 문제** | `C2143`은 MSVC 컴파일러의 진단이며, 현재 빌드가 컴파일 단계에서 실패했다. |
| 2 | **링크 문제** | 컴파일은 끝났지만 링커가 필요한 정의를 찾지 못해 `undefined reference`를 보고했다. |
| 3 | **논리 문제** | 프로그램은 끝까지 실행되었지만 요구한 평균이 아니라 합계를 출력했다. |
| 4 | **실행 중 문제** | 빌드는 성공했고 실행도 시작되었지만, 특정 입력에서 정상적으로 결과를 내며 작업을 완료하지 못하고 도중에 끝났다. |
| 5 | **논리 문제** | 빌드와 실행은 완료되었지만 출력이 의도한 문자열과 다르다. |

### 상세해설

이 문제에서는 **언제 문제가 드러났는가**를 먼저 보는 것이 중요하다.

- **컴파일 단계 문제:** 소스가 언어 규칙이나 도구 설정에 맞지 않아 컴파일을 정상적으로 끝내지 못한다.
- **링크 문제:** 컴파일된 조각은 만들어졌지만 필요한 이름과 정의를 연결하지 못한다.
- **실행 중 문제:** 빌드는 성공하고 실행이 시작되었지만, 실행 중 발생한 문제 때문에 정상적인 진행이나 완료가 어려워진다.
- **논리 문제:** 빌드와 실행은 끝났지만 결과나 동작이 의도한 명세와 다르다.

특히 3번처럼 계산 결과가 틀렸다는 사실만으로 실행 중 문제라고 분류하지 않는다. 이 장의 분류에서는 프로그램이 정상적으로 끝까지 실행되었는데 결과가 잘못되었다면 **논리 문제**다.

## 문제 4. `.c`와 `.cpp`

### 정답

1. `Source.cpp`는 일반적인 MSVC 설정에서 기본적으로 **C++ 규칙**으로 컴파일된다.
2. 지금 우연히 오류 없이 빌드된다고 해도 C와 C++는 서로 다른 언어이므로 충분한 이유가 되지 않는다. 현재 코드는 두 언어에서 모두 받아들여질 수 있어도, 나중에 추가한 코드가 한쪽에서 실패하거나 서로 다른 규칙의 영향을 받을 수 있다.
3. 솔루션 탐색기에서 파일 이름이 `.cpp`인지 확인하고, **`Source.cpp` → `Source.c`**로 바꾼다.

### 상세해설

MSVC는 별도 지정이 없으면 확장자를 보고 소스 언어를 판단한다. `.c`는 C로, `.cpp`는 C++로 처리한다. 따라서 C를 배우는 프로젝트에서는 파일 내용이 “C처럼 보이는가”보다 **파일이 실제로 C 규칙으로 컴파일되고 있는가**가 중요하다.

MSVC에는 C로 강제 컴파일하는 `/TC` 같은 옵션도 있지만, 이 책의 초보자용 기본 방법은 그런 옵션에 의존하는 것이 아니라 **소스 파일 확장자를 `.c`로 사용하는 것**이다.

## 문제 5. 옵션 고르기

### 정답

#### 1. 표 채우기

| 목적 | MSVC | GCC |
|---|---|---|
| C17 표준 모드 | `/std:c17` | `-std=c17` |
| 이 책의 경고 설정 | `/W4` | `-Wall -Wextra` |

#### 2. 잘못된 명령과 설명 고치기

네 항목은 모두 잘못되었으며 다음과 같이 고친다.

**A. GCC 명령**

잘못된 명령:

`gcc /std:c17 /W4 hello.c -o hello`

바른 명령:

`gcc -std=c17 -Wall -Wextra hello.c -o hello`

이유: `/std:c17`과 `/W4`는 MSVC 방식의 옵션이다. GCC에서는 `-std=c17`, `-Wall`, `-Wextra`를 사용한다.

**B. MSVC 명령**

잘못된 명령:

`cl -std=c17 -Wall -Wextra hello.c`

바른 명령:

`cl /std:c17 /W4 hello.c`

이유: MSVC는 GCC와 다른 옵션 표기를 사용한다.

**C. `-Wall` 설명**

잘못된 설명:

> `-Wall`을 쓰면 GCC가 알고 있는 모든 경고가 켜진다.

바른 설명:

> `-Wall`은 GCC의 여러 경고 가운데 폭넓게 선택된 묶음을 켜지만, GCC가 지원하는 모든 경고를 켜는 옵션은 아니다. 이 책은 여기에 `-Wextra`를 함께 사용한다.

**D. Visual Studio의 기본 경고 수준**

잘못된 설명:

> Visual Studio의 새 프로젝트는 처음부터 경고 수준이 `/W4`로 설정되어 있다.

바른 설명:

> 이 장의 기준에서 Visual Studio IDE의 기본 경고 수준은 일반적으로 `/W3`이므로, 이 책에서는 `/W4`로 직접 바꾸어 사용한다.

### 상세해설

컴파일 옵션은 C 소스 문법이 아니라 **도구 모음에 전달하는 설정**이다. 따라서 같은 목적이라도 MSVC와 GCC의 표기가 다르다. 이 책에서는 표준 모드와 경고 수준을 매번 같은 기준으로 맞추기 위해 다음 조합을 사용한다.

- MSVC: `/std:c17 /W4`
- GCC: `-std=c17 -Wall -Wextra`

## 문제 6. 진단 메시지 해석하기

### 정답

첫 번째 메시지는 **MSVC**, 두 번째 메시지는 **GCC**의 것이다.

- MSVC: `report.c(12): error C2143: ...`
- GCC: `report.c:11:30: error: ...`

MSVC는 `파일(줄)` 형태와 `C2143` 같은 진단 번호를 사용한다. GCC는 `파일:줄:열:` 형태로 위치를 표시한다.

두 메시지가 서로 다른 줄을 가리킬 수 있는 이유는, 세미콜론이 빠진 사실을 컴파일러가 바로 그 자리에서 확정하지 못할 수 있기 때문이다. 다음 토큰인 `return`을 읽고 나서야 앞 문장이 끝나지 않았다는 사실이 분명해질 수 있다.

따라서 실제로 고쳐야 할 가능성이 가장 높은 곳은 **이전 문장의 끝, 특히 11번 줄 끝**이다.

### 상세해설

오류 메시지의 줄 번호는 “틀린 문자가 반드시 이 줄에 있다”는 뜻이 아니라, 컴파일러가 **문제를 확실히 인식한 위치**일 수 있다. 그래서 보고된 줄이 멀쩡해 보이면 바로 앞줄도 함께 확인해야 한다.

이 예에서는 GCC가 11번 줄의 세미콜론이 있어야 할 위치를 직접 가리키고, MSVC는 다음 12번 줄에서 `return`을 읽은 뒤 문제를 보고했다. 두 진단은 서로 모순되는 것이 아니라 같은 원인을 서로 다른 시점에 발견한 것이다.

## 문제 7. 오류가 많을 때의 작업 순서

### 정답

권장 작업 순서는 다음과 같다.

1. 오류 목록의 **위쪽부터** 읽는다.
2. 처음으로 뜻이 분명한 오류를 찾는다.
3. 보고된 위치와 그 주변, 특히 바로 앞줄을 확인한다.
4. 그 오류의 원인이 되는 문제 하나를 고친다.
5. **다시 빌드한다.**
6. 줄어든 오류 목록을 다시 위에서부터 읽는다.
7. 남은 오류에 대해 같은 과정을 반복한다.

### 상세해설

초기의 문법 실수 하나가 뒤쪽 코드를 잘못 해석하게 만들면 실제 원인은 하나인데도 여러 개의 추가 진단이 연달아 나타날 수 있다. 따라서 23번째 오류부터 고치면 실제로는 멀쩡한 코드를 잘못 바꿀 가능성이 있다.

문제 하나를 고친 뒤 곧바로 다시 빌드하면, 그 문제 때문에 생긴 **2차 진단**들이 한꺼번에 사라질 수 있다. 그러면 남은 실제 문제를 더 쉽게 찾을 수 있다.

“마지막으로 성공한 빌드를 실행할까요?”라는 질문이 나오면, **현재 수정 내용을 확인하려는 목적이라면 실행하지 않는 것이 맞다.** 현재 빌드는 실패했으므로 그 실행 파일은 최신 수정 내용을 반영한 것이 아닐 수 있다. 디스크에 예전 실행 파일이 남아 있을 수 있으며, 그것을 실행하면 이전 소스 상태의 프로그램을 보고 현재 수정이 성공했다고 오해할 수 있다.

현재 편집 내용을 확인하려면 오류를 먼저 고쳐 **이번 빌드가 성공한 뒤** 실행해야 한다.

## 문제 8. 파이프라인 추적하기 〔심화·도전〕

### 정답

#### 8-1. 처음 빌드할 때

개념적인 흐름은 다음과 같다.

~~~text
calc.c
  ↓ 전처리
전처리된 calc 소스
  ↓ 컴파일
낮은 수준의 중간 표현
  ↓ 어셈블
calc.obj
       \
        \
         +──→ 링크 ──→ <프로젝트명>.exe
        /
       /
report.obj
  ↑ 어셈블
낮은 수준의 중간 표현
  ↑ 컴파일
전처리된 report 소스
  ↑ 전처리
report.c
~~~

같은 흐름을 위에서 아래로 나누어 쓰면 다음과 같다.

~~~text
calc.c   → 전처리 → 컴파일 → 어셈블 → calc.obj
report.c → 전처리 → 컴파일 → 어셈블 → report.obj

calc.obj + report.obj → 링크 → <프로젝트명>.exe
~~~

Windows에서 MSVC를 사용할 때 목적 파일은 보통 **`calc.obj`**, **`report.obj`**처럼 만들어진다.

문제에서 프로젝트 이름을 주지 않았으므로 실행 파일 이름을 임의로 `calc.exe`나 `report.exe`라고 정하면 안 된다. **`<프로젝트명>.exe`** 또는 “프로젝트의 출력 설정으로 정한 `.exe` 파일”이라고 쓰는 것이 적절하다.

실제 도구 모음은 전처리 결과나 어셈블리 수준의 중간 결과를 별도 파일로 저장하지 않을 수 있다. 위 그림은 각 단계의 **개념적인 흐름**을 나타낸다.

#### 8-2. `report.c`만 수정한 뒤 다시 빌드할 때

다음 조건을 가정한다.

- `report.c`만 바뀌었다.
- 두 파일이 함께 의존하는 헤더나 다른 의존 파일은 바뀌지 않았다.
- 기존 `calc.obj`가 여전히 유효하다.

그렇다면 `report.c`는 다시

**전처리 → 컴파일 → 어셈블**

단계를 거쳐 **`report.obj`를 새로 만들어야 한다.**

반면 `calc.c`는 변경되지 않았으므로 유효한 `calc.obj`가 남아 있다면 다시 컴파일할 필요가 없다.

그러나 최종 실행 파일에는 새 `report.obj`가 반영되어야 하므로,

**`calc.obj + 새 report.obj → 링크 → 실행 파일 갱신`**

과정은 다시 수행해야 한다.

즉, “`report.c`만 다시 처리하면 끝”이 아니라 **마지막 링크도 다시 필요하다.** 실제 빌드 시스템은 이런 재빌드 범위를 자동으로 판단하여 필요한 작업만 수행할 수 있다.

#### 8-3. Windows 실행 파일이 Unix에서 실행되지 않을 때

Windows에서 만든 실행 파일은 특정 운영체제, 실행 파일 형식, 프로세서·런타임 환경을 대상으로 만들어진 결과물이므로 Unix 계열 운영체제에서 그대로 실행된다고 가정하면 안 된다.

친구에게는 보통 다음 자료를 전달해야 한다.

- 소스 코드
- 필요한 헤더 파일
- 필요한 라이브러리
- 빌드 방법과 필요한 설정
- 실행에 필요한 데이터나 기타 외부 자원

친구는 Unix 환경에서 사용할 수 있는 **호환되는 C 도구 모음**으로 소스 코드를 다시 빌드해야 한다. 프로그램이 Windows 전용 API나 다른 플랫폼 의존 기능을 사용했다면 일부 소스 수정이 필요할 수도 있다.

### 상세해설

이 문제는 목적 파일이 **소스 파일마다 따로 만들어진다**는 점과, 마지막에 링커가 그 목적 파일들을 모아 하나의 실행 파일을 만든다는 점을 확인하는 문제다.

또한 C의 이식성은 “같은 `.exe` 파일이 모든 운영체제에서 실행된다”는 뜻이 아니다. 주로 **소스 코드를 다른 환경으로 옮기고 그 환경에 맞게 다시 빌드하기 쉽게 만드는 것**과 관련된다.

### 다른 답이 가능한 기준

1번의 실행 파일 이름은 프로젝트 이름과 출력 설정에 따라 달라질 수 있다. 따라서 특정 이름을 억지로 정하지 않고, **두 목적 파일이 링크되어 프로젝트의 실행 파일이 만들어진다는 관계**를 정확히 표현하면 된다.

2번에서는 변경되지 않은 `calc.c`의 재컴파일을 생략할 수 있다고 답하되, `calc.obj`가 유효하고 공유 의존 파일이 바뀌지 않았다는 조건을 밝혀야 한다. 그리고 **최종 링크는 다시 수행해야 한다.**
